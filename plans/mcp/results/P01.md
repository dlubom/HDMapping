## Przegląd, decyzje i otwarte warunki

W pierwszej sesji niezależny recenzent przejrzał kod, kontrakty, CMake/install/CI i pakowanie. Wykrył, że literalne `BOOL=ON` pomija poprawne wartości `1`, `TRUE`, `YES`. Naprawa: CMake generuje `hdmapping-mcp-enabled.txt` jako 0/1, oba skrypty korzystają z niego. Próbka CMake odtworzyła pierwotny problem; po poprawce ON/1/YES/TRUE → 1, OFF/0/NO/FALSE → 0, wszystkie PASS. Pozostałych Critical/Important brak.

W kontynuacji nowy niezależny recenzent sprawdził cały zakres `8d8ec2a..b78494e` wraz z poprawką `1297fbf`; nie zgłosił uwag Critical/Important/Minor. Raport/status sprawdzono osobno pod kątem spójności, lokalnych odsyłaczy i diffu.

**Uwaga Visual Studio naprawiona w `1297fbf`.** `CMAKE_CROSSCOMPILING` nie wykrywa wszystkich wyborów `-A`; [CMAKE_VS_PLATFORM_NAME](https://cmake.org/cmake/help/latest/variable/CMAKE_VS_PLATFORM_NAME.html) podaje rzeczywisty cel generatora. Tymczasowy harness `cmake -P` włącza prawdziwy `cmake/go.cmake`, ustawia `CMAKE_CROSSCOMPILING=FALSE`, generator Visual Studio, host AMD64/ARM64 i cel x64/ARM64/Win32/ARM64EC; podstawiony program Go odpowiada wyłącznie zgodną wersją hosta. Przed poprawką wszystkie sześć niezgodnych kombinacji przechodziło konfigurację (RED). Po poprawce przechodzą tylko AMD64/x64 i ARM64/ARM64; pozostałe sześć kończy się błędem „native Visual Studio target” (GREEN). Powtórzono na dokładnym `1297fbf`. To kontrola logiki CMake, nie uruchomienie VS/Go Windows. Natywne CMake macOS nadal konfiguruje/buduje się poprawnie. Cross/universal build pozostaje poza obsługiwanym zakresem.

Inne rozstrzygnięcia: osobny moduł narzędzi chroni zależności produktu; custom target korzysta z cache Go, bo zależność plikowa od imported executable gubiła regułę generowania w Makefiles (odtworzono w minimalnym projekcie, finalny build PASS). Warunki procesów/GUI/danych i P02+ pozostają poza P01. Kwalifikacji odłożonych przez właściciela nie ponawiano. Konfiguracja ARM macOS automatycznie nakłada istniejący patch `fbow_non_x86.patch`; nie jest zmianą submodule commit ani zakresem P01, po buildach odwrócono dokładnie ten patch i potwierdzono czysty stan submodułów, bez zmiany ich commitów.

Do pełnego odbioru nadal potrzebne są: Windows 11 (Go/testy, build/install ON/OFF, relokacja), pełne build/install OFF Ubuntu i Windows Server oraz zakończone właściwe CI poprawki `1297fbf`, w tym pakowanie macOS. CMake install/relokacja ON macOS oraz instalacja/relokacja pakietu Debian są wykonane; wiki jest już opublikowana. Braki danych oraz Windows/Linux/Claude z P00 pozostają otwarte, bez ponownego zaliczenia. **Następny czat: kontynuacja P01 na mcp/p01**, od zweryfikowanego zdalnego SHA dostarczenia. Nie rozpoczęto P02. Jedna karta, wymagane kontrole jakości, raport, przegląd, commit/push, kolejny prompt i STOP.

## Opublikowany tekst wiki forka

> **Optional MCP build (development):** Configure with `-DBUILD_WITH_MCP=ON` to build the local stdio adapter. The default remains OFF until the full MCP feature is qualified. CMake uses exactly Go 1.27.4 or downloads the official host archive with a pinned SHA256; no manual Go bootstrap is needed. Builds require network access for the pinned Go modules. Installed packages do not require Go, Python or Node. The adapter is installed by the existing applications component and platform packaging, using the common product version and binary prefix. The only current tool is `server_info`; processing and job control are not yet available. Use the executable from the moved installation as the MCP client's stdio command. Developer checks: enable `HDMAPPING_MCP_QUALITY=ON`, build `mcp-check` and `mcp-check-controls`; Linux amd64 additionally enables `HDMAPPING_MCP_RACE=ON` and runs `mcp-race`. These developer checks require Python 3 and, for race tests, cgo plus a C compiler. Only native single-architecture builds are currently supported.
