## Polecenia odtwarzające

```sh
cmake -S . -B build-p01 -DCMAKE_BUILD_TYPE=Release \
  -DBUILD_WITH_MCP=ON -DBUILD_TESTING=ON -DHDMAPPING_MCP_QUALITY=ON \
  -DFREEGLUT_COCOA=ON -DHDMAPPING_GO_FORCE_DOWNLOAD=ON
cmake --build build-p01 --target hdmapping_mcp_build mcp-check mcp-check-controls
ctest --test-dir build-p01 -L mcp --output-on-failure
# Linux amd64, gdy wykonywany jest jego odbiór:
cmake -S . -B build-p01 -DHDMAPPING_MCP_RACE=ON
cmake --build build-p01 --target mcp-race mcp-check-controls
```

Zwykły pełny build/install: `cmake --build build -j4`, `ctest --test-dir build --output-on-failure`, `cmake --install build --prefix <katalog> --component applications`. OFF: `cmake -S . -B build -DBUILD_WITH_MCP=OFF`; ON: analogicznie `=ON`. MacOS używa istniejącego `macos_bundle_toolkit/create_dir_bundle.sh`; Windows `deploy_mandeye.bat`; Debian obecnego CPack. Nie ma osobnego wydania MCP. `HDMAPPING_MCP_QUALITY` i `HDMAPPING_MCP_RACE` są opcjami deweloperskimi, nie wymaganiami pakietu.

## Przegląd, decyzje i otwarte warunki

Niezależny recenzent przejrzał kod, kontrakty, CMake/install/CI i pakowanie. Wykrył, że literalne `BOOL=ON` pomija poprawne wartości `1`, `TRUE`, `YES`. Naprawa: CMake generuje `hdmapping-mcp-enabled.txt` jako 0/1, oba skrypty korzystają z niego. Próbka CMake odtworzyła pierwotny problem; po poprawce ON/1/YES/TRUE → 1, OFF/0/NO/FALSE → 0, wszystkie PASS. Pozostałych Critical/Important brak.

**Odłożona uwaga Minor:** diagnostyka konfiguracji Visual Studio z architekturą celu inną niż host; CMAKE_CROSSCOMPILING nie wykrywa wszystkich takich wariantów. Obecny zakres to natywne buildy, bez obietnicy cross/universal build. Koszt otwartego przypadku: możliwe pomieszanie architektury Go/C++ przy takim niestandardowym generatorze; nie jest to dowód wykonania ani zaliczenia Windows.

Inne rozstrzygnięcia: osobny moduł narzędzi chroni zależności produktu; custom target korzysta z cache Go, bo zależność plikowa od imported executable gubiła regułę generowania w Makefiles (odtworzono w minimalnym projekcie, finalny build PASS). Warunki procesów/GUI/danych i P02+ pozostają poza P01. Kwalifikacji odłożonych przez właściciela nie ponawiano. Konfiguracja ARM macOS automatycznie nakłada istniejący patch `fbow_non_x86.patch`; nie jest zmianą submodule commit ani zakresem P01, po buildach odwrócono dokładnie ten patch i potwierdzono czysty stan submodułów, bez zmiany ich commitów.

Do pełnego odbioru nadal potrzebne są brakujące wykonania P01 na platformach, zakończone właściwe CI i dostępna wiki forka. Braki danych oraz Windows/Linux/Claude z P00 pozostają otwarte, bez ponownego zaliczenia. **Następny czat: kontynuacja P01 na mcp/p01**, od zweryfikowanego zdalnego SHA dostarczenia. Nie rozpoczęto P02. Jedna karta, wymagane kontrole jakości, raport, przegląd, commit/push, kolejny prompt i STOP.

## Gotowy tekst do wiki forka

> **Optional MCP build (development):** Configure with `-DBUILD_WITH_MCP=ON` to build the local stdio adapter. The default remains OFF until the full MCP feature is qualified. CMake uses exactly Go 1.27.4 or downloads the official host archive with a pinned SHA256; no manual Go bootstrap is needed. Builds require network access for the pinned Go modules. Installed packages do not require Go, Python or Node. The adapter is installed by the existing applications component and platform packaging, using the common product version and binary prefix. The only current tool is `server_info`; processing and job control are not yet available. Use the executable from the moved installation as the MCP client's stdio command. Developer checks: enable `HDMAPPING_MCP_QUALITY=ON`, build `mcp-check` and `mcp-check-controls`; Linux amd64 additionally enables `HDMAPPING_MCP_RACE=ON` and runs `mcp-race`. These developer checks require Python 3 and, for race tests, cgo plus a C compiler. Only native single-architecture builds are currently supported.
